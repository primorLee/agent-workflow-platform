# Security policy

## Reporting a vulnerability

Do not open a public issue for an undisclosed vulnerability. Follow the
repository's [root security policy](../../SECURITY.md) and use GitHub's private
security-advisory flow for this repository. Include reproduction steps, impact,
and any suggested mitigation.

## Supported versions

This extraction has no stable release. Security fixes land on the default
branch until a versioned support policy is published.

## Security boundaries

- The agent opens no listening socket; it initiates the broker connection.
- Remote deployments must use `wss://` with the operating-system trust store.
  Plain `ws://` is restricted to literal loopback development endpoints.
- `tls_cert_pin` is parsed by configuration but is not enforced by the current
  dialer. Do not treat it as an active control.
- The binary accepts API keys from YAML or `AWP_AGENT_API_KEY`. The installer
  requires a local `--api-key-file` so the secret is not placed in argv, then
  writes a restricted service environment file. A same-user process or host
  administrator may still inspect process memory or environment.
- The built-in runner never invokes `sh -c`, but it is a trusted task launcher,
  not an OS sandbox. Task stdout/stderr is sent to the control plane and may
  contain sensitive data generated by task code.
- Callers and new adapters are responsible for preventing credentials from
  entering task arguments, output, workflow state, artifacts, and logs.

## Host hardening

The checked-in systemd template runs as the component-specific unprivileged
`awp-vm-agent` account, drops capabilities, restricts common kernel surfaces,
and limits writable paths for the checked-in `echo` adapter. These settings are baseline hardening, not
containment against malicious code running as the same user. Review and test
the unit whenever an adapter needs additional files, devices, sockets, or JIT
memory. Use a separate container, VM, or operating-system identity for
untrusted workloads.

## Installation and updates

The installer has no default release endpoint or signing key. It requires an
explicit immutable HTTPS source, caller-supplied SHA-256 digest, and a local
reviewed public-key file, and it verifies both the digest and detached
signature. `file://` is accepted only in exact test mode and signature
verification remains mandatory. Manual installation owns only a closed set of
paths recorded in `/etc/awp-vm-agent/.awp-install-owner-v1`; it refuses existing
accounts or paths without that exact root-owned marker. The normal uninstaller
retains the dedicated identity and persistent state, while `--purge`, one-line
installation, and all package lifecycle hooks fail with status 77 in this
source preview.

## Known limitations

- The public main wires the WebSocket dialer, dispatcher, runner, and watchdog.
  Queue/replay, artifact upload, and telemetry packages are not all enabled in
  that composition.
- Panic reports are stored locally and may contain paths or stack data.
- The public Python control plane does not provide the VM agent's richer
  WebSocket protocol endpoint; use the mock-broker tests or compose a compatible
  endpoint before starting the service.
